## 基础题（概念辨析）

1. Skill 的三级渐进加载是什么？每一级的内容在什么时机进入上下文？

2. 判断对错，并说明理由：安装了一个 Skill 之后，模型的能力发生了改变，因为它的参数被更新了。（　）

## 应用题（动笔设计）

3. 你要给一个 AI 助手写一个"周报生成"技能的 description（触发描述）。以下两个版本哪个更容易被正确触发？为什么？
   - 版本 A：`处理各种文档相关的任务`
   - 版本 B：`根据本周的工作记录、提交记录和日程，生成结构化周报（Markdown 格式），当用户要求"写周报""总结本周工作"时使用`

4. 按笔记中的数据：50 个技能、正文平均 2000 tokens、描述 30 tokens，一轮对话最多命中 1 个技能。计算"全量常驻"和"按需加载"两种方案的 token 占用，并算出节省比例。

## 挑战题（写代码验证）

5. 给 `智能体技能-示例.py` 的 `match_skill` 加上"误触发"测试：构造一条**应该**命中 data-visualization 却可能被其他技能抢先的请求（例如"给我生成一张图表的学习笔记"），观察命中结果；然后改进匹配逻辑（如给关键词设权重，"学习资料"类关键词权重更高），让该请求正确命中 concept-learning-material。
   提示：`match_skill` 目前是"命中数最多者胜"，可改为 `sum(权重)`，再观察同一条请求的命中变化。

**第 1 题**：第一级 = name + description（常驻，约几十 token/技能，负责被"看见"）；第二级 = SKILL.md 正文（任务匹配、触发技能时加载）；第三级 = references / assets / scripts（执行中要用到才读入，脚本甚至可以只运行不读入）。

**第 2 题**：错。Skill 不改模型参数（那叫微调/训练），它只是在**运行时**把指令和资源注入上下文。同一个模型，装不装 Skill，能力边界相同，但执行流程的规范性和产出的质量可以天差地别——"手册让员工表现更专业，但没有换脑子"。

**第 3 题**：版本 B。原因有三：① 列出了**具体动作**（生成结构化周报）和**输入物**（工作记录、提交记录、日程），与用户请求的词汇直接重叠，容易匹配；② 给出了**触发示例**（"写周报""总结本周工作"）；③ 版本 A 的"处理各种事务"过于宽泛，模型无法判断何时该用它（也更容易在不该用时乱触发）。描述是技能的"生死线"——太窄触发不了，太宽乱触发。

**第 4 题**：全量常驻 = 50 × 2000 = 100,000 tokens；按需加载 = 50 × 30 + 2000 = 3500 tokens（描述常驻 1500 + 命中 1 个技能正文 2000）。节省 = (100000 - 3500) / 100000 = **96.5%**。

**第 5 题**：请求"给我生成一张图表的学习笔记"会同时命中两个技能的关键词：concept-learning-material 的"生成、笔记"（2 个）和 data-visualization 的"图表"（1 个），当前"命中数最多者胜"会正确命中前者；但把请求改成"画一张图，再配点笔记"则 data-visualization（"画"）与 concept（"笔记"）各 1 个，平局由遍历顺序决定——这就是不稳定根源。加权方案参考：

```python
WEIGHTS = {"生成": 2, "学习资料": 3, "笔记": 3, "练习": 2, "画": 2, "图表": 1, "直方图": 1}
def match_skill(query):
    best, best_score = None, 0
    for name, s in SKILLS.items():
        score = sum(WEIGHTS.get(k, 1) for k in s["keywords"] if k in query)
        if score > best_score:
            best, best_score = name, score
    return best
```

结论：真实系统中触发判断由大模型完成，比关键词匹配聪明得多，但"描述里体现区分度、给触发示例"这两条设计原则完全相同。
