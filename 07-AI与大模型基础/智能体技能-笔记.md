# 智能体技能（Skill）

> 所属章节：07-AI与大模型基础 ｜ 建议学习时长：1 小时 ｜ 难度：⭐⭐☆

## 一句话理解

Skill 是打包好的**专项操作手册**（指令 + 模板 + 脚本 + 参考资料），平时只让几十 token 的"目录条目"常驻上下文，被触发时才把上千 token 的完整内容加载进来——让通用模型瞬间变身领域专家。

## 直观解释

想象你入职一家公司，公司有两种做法：

- **做法 A**：把所有岗位的 SOP 手册全文塞给你背下来——你脑子（上下文）根本装不下，而且大部分工作今天用不上
- **做法 B**：给你一张**手册目录**（每本一句话介绍），用到哪本再翻开哪本

做法 B 就是 Skill 的设计哲学。它直接呼应了上一个概念：**上下文窗口是稀缺资源**（O(N²) 的计算量），而 Agent 要执行的任务种类是无限的——"按需加载"是唯一兼顾广度与深度的方案。

一个 Skill 通常包含：

```
skill-name/
├── SKILL.md          # 主文件：元数据（名称+描述，用于触发）+ 操作指令正文
├── assets/           # 模板等产出物（生成结果时直接复制使用）
├── references/       # 参考资料（需要时才读入）
└── scripts/          # 可执行脚本（甚至可以不读入、直接运行）
```

## 数学定义

Skill 的精髓是一套**三级渐进加载**机制，用极小的常驻成本换取按需的完整能力：

$$
\text{常驻成本} = \sum_{i=1}^{M} \text{desc\_tokens}(s_i) \quad \text{（M 个技能的描述，通常每个约 20~50 token）}
$$

- **第一级（常驻）**：所有技能的 name + description，始终在上下文中，负责"被看见、被触发"
- **第二级（触发时）**：完整 SKILL.md 指令正文（通常 1K~5K token），仅在任务匹配时加载
- **第三级（按需）**：references / assets / scripts，执行过程中要用到才读取，甚至只运行不读

对比"全部正文常驻"：$M$ 个技能平均每个 $B$ token 正文，常驻成本从 $O(M \times B)$ 降到 $O(M \times d) + B$（$d \ll B$ 为描述长度）。

## Python 实战

以下结果由 `智能体技能-示例.py` 实际运行得出（3 个技能：正文分别 1800 / 1500 / 1200 tokens，全部常驻需 4500 tokens）：

```
用户请求: 帮我生成假设检验的学习资料
  命中技能: concept-learning-material（关键词: 生成、学习资料）
  本次加载: 描述常驻 60 + 正文 1800 = 1860 tokens
  对比全部正文常驻 4500 tokens，本次节省 2640

用户请求: 给我画一个成绩分布的直方图
  命中技能: data-visualization（关键词: 画、直方图）
  本次加载: 描述常驻 60 + 正文 1500 = 1560 tokens
  对比全部正文常驻 4500 tokens，本次节省 2940

用户请求: github 推送失败，帮我推上去
  命中技能: github-push-api（关键词: github、推送）
  本次加载: 描述常驻 60 + 正文 1200 = 1260 tokens
  对比全部正文常驻 4500 tokens，本次节省 3240

用户请求: 今天天气怎么样？
  未命中任何技能 -> 加载 0（技能描述仍常驻 60 tokens）

4 轮请求累计节省: 13320 tokens
```

**解读**：与"4500 tokens 全量常驻"相比，按需加载平均每轮只用约 1560 tokens（不足 35%）；第四条闲聊请求未命中任何技能，零加载。省下的空间可以装更多对话历史或参考资料——**窗口没变大，能办的事变多了**。

## 常见误区

1. **"Skill 是给模型装插件/微调"** —— 都不是。Skill 不改变模型本身（权重一丁点都不动），它只是在运行时注入**指令和资源**。模型还是那个模型，只是"上岗前读了手册"。
2. **"装了 Skill 就一定生效"** —— 不一定。是否触发由模型根据 description 判断；描述写得含糊（如"处理各种事务"），模型永远匹配不上，技能就成了死库存。
3. **"Skill 内容越全越好"** —— 错。正文塞得太长会挤占上下文、稀释关键指令。大而全的资料应放 references/ 里按需读取，SKILL.md 本身要精炼。

## 与其他概念的联系

- 前置知识：**上下文**（为什么必须按需加载——窗口稀缺且 O(N²) 昂贵）
- 上游概念：**Agent**（Skill 是 Agent 工具箱里的"知识型工具"：脚本负责"做"，指令负责"怎么做"）
- 对比易混：**系统提示词（System Prompt）**（每轮常驻、全局生效、适合放身份和铁律）vs **Skill**（按需加载、专项生效、适合放流程和模板）。本仓库的"概念学习资料生成"就是一个真实运行的 Skill：描述常驻，用户说"生成 XX 学习资料"时被触发。

## 自测问题

1. Skill 的三级渐进加载分别是什么？各自在什么时机进入上下文？
2. 为什么说 Skill 的 description 是"生死线"？写得太宽和太窄分别有什么后果？
3. 假设有 50 个技能、每个正文 2000 tokens：全量常驻 vs 按需加载（描述每个 30 tokens），一轮对话中最多命中 1 个技能时，两种方案各占多少 token？
